# 2026-11-25: Super Mario 3D Land, frame pacing, build 0.1.2

Evidence: **device test** by the project owner, build `753f9a6`, system set to 60 Hz, Turnip
driver, warm shader cache. World 1-1 played twice.

| Session | Owner's description | Length |
| --- | --- | --- |
| 19:57:18 | Bottom screen off | 161 s, three pauses |
| 20:00:22 | Bottom screen on | 48 s, one pause |

## What the displays are doing

- Android reports both panels in their 60 Hz mode (`60.000004`), with a 120 Hz mode
  available on each. Neither window has a preferred mode set: upstream's request for 60 Hz
  looks for a mode reporting exactly `60.0` and so does nothing on this device.
- Measured from actual display times, both panels refresh at **59.73 Hz** (16.74 ms), with
  near-identical timestamps on the two.
- The emulator runs at the 3DS rate, **59.84 frames per second**. That is 0.11 frames per
  second more than the panels can show, so one frame must be discarded about every 9 s.
- `use_vsync` is off, so both swapchains use MAILBOX presentation (6 images each): a newer
  image replaces one that has not been shown yet.
- `VK_GOOGLE_display_timing` was available; all display times below are actual display
  times, not submission times.

## The 8.3 / 25 ms pattern

It is real on the emulation thread but is not a display mode. Emulated frames alternate
between about 1 ms and 8 to 10 ms of work. The speed limiter sleeps after each frame so that
limiter exits are evenly spaced, but upstream timestamps the frame, and submits it for
presentation, after the work and before the sleep. Submission times therefore alternate
around 8 and 25 ms apart.

## What reached the screens (steady gameplay)

| Measure | Bottom off (50 to 100 s) | Bottom on (15 to 47 s) |
| --- | --- | --- |
| Frames submitted per second | 59.84 | 59.84 |
| New images shown per second, top screen | 59.73 | 55.09 |
| Frames never shown, top screen | 5 of 2,992 (0.2%) | 151 of 1,914 (7.9%) |
| Frames never shown, bottom window | 6 of 2,992 | 173 of 1,914 (9.0%) |
| Median submit-to-display delay | 44 ms | 59 ms |

- Bottom off: the screen showed a new image on essentially every refresh. The only losses
  are the one-in-nine-seconds frame the rate mismatch forces.
- Bottom on: frames are lost in bursts about every 10 s, which matches the beat between
  59.84 and 59.73 Hz. Each lost frame comes with the previous image held for two refreshes
  (33.5 ms). Both windows lose frames at the same moments.

## Emulation thread

- Presentation does not block it: waiting for a free presentation frame averages 0.07 ms
  per frame, GPU waits 0.07 ms, render worker waits 0.6 ms.
- No frame in steady gameplay had more than 30 ms of work in either session.
- Frames with long work occur at boot (0 to 6 s, at the same moments in both sessions) and
  right after returning from a pause or a swapchain rebuild. They are CPU time not explained
  by file reads, GPU waits or compilation. One 1.1 s frame followed a pause in the first
  session.

## Caveats

- One run of each, of different lengths, and the second is short.
- It is not yet confirmed what "bottom screen off" changed at the system level: the
  secondary window kept presenting in both sessions.
- The mechanism by which the second physical display increases frame loss is a hypothesis
  (later image latching with two displays, combined with uneven submission times and
  MAILBOX), not a measurement.
